H. HEALTH WINDOW, ZERO-DOWNTIME, AND PREMATURE-ROLLBACK PREVENTION
-------------------------------------------------------------------------------

Render health checks are part of the cutover gate. For a new deploy, Render
normally keeps the existing instances serving until the new instances pass
health checks; a new deploy can remain in health evaluation for up to the
platform's documented window before Render cancels it.

Therefore:

1. Do not call a deployment failed merely because the canonical domain still
   serves the previous version while the new instances are building or being
   health-checked.
2. Monitor the exact Render deploy ID and state first; use canonical-domain
   polling as verification, not as the sole deployment-status source.
3. Do not launch an automatic rollback while Render is still safely serving the
   last version and the new deploy remains within its documented build/start/
   health window, unless a definitive fatal error is already proved.
4. Configure the Render health path to be bounded, fast, non-destructive, and
   representative of whether the service can safely receive traffic.
5. Use a separate readiness route when a required dependency materially affects
   safe service. Do not make a transient optional integration outage take the
   entire portal offline when graceful degradation is the correct design.
6. Record persistent-disk use. Do not promise ordinary zero-downtime replacement
   or code-only rollback where persistent state prevents it.

-------------------------------------------------------------------------------
I. ROLLBACK ELIGIBILITY — FAST WHEN SAFE, NEVER FICTIONAL
-------------------------------------------------------------------------------

Prefer Render's native rollback to a retained successful deploy when available
and safe because it can reuse a recent build artifact and complete faster than
rebuilding an old commit. Before automatic rollback, verify all of the
following:

- the target is a distinct earlier successful Render deploy;
- its retained build artifact is still available under the current workspace
  plan;
- the release ZIP, commit, version, deploy ID, health contract, and migration
  state are known;
- the failed release did not make a destructive, irreversible, or incompatible
  database or persistent-disk change;
- current configuration differences do not make the old artifact unsafe;
- the rollback will not immediately be overwritten by an unchanged bad
  production branch and active auto-deploy.

Render rollback does not restore all current service configuration or state.
Persistent disks retain their state. Custom domains remain current. Environment
groups can reflect current values rather than the historical deploy's complete
state. Record these facts in rollback eligibility.

CORRECTED DEPLOYMENT-MODE SELECTION

MODE N — NATIVE RENDER `AFTER CI CHECKS PASS`

This is the fastest recurring mode only when the production branch is cleanly
eligible. Render waits for all CI checks it detects for the linked branch
commit, not merely the check that GitHub marks as required. Therefore use Mode N
only when:

- the service is Git-backed and linked to the intended production branch;
- the exact qualified tree can be promoted safely to that branch;
- every check normally emitted for that production commit is deterministic,
  bounded, and expected to conclude successfully;
- no intentionally failing, permanently pending, optional external, or
  path-filtered workflow can leave the commit in an ambiguous state;
- the production gate has a stable name and cannot be skipped for a runtime,
  dependency, workflow, migration, health, asset, or deployment change;
- Render is configured with `autoDeployTrigger: checksPass` or the exact current
  dashboard equivalent;
- the builder can monitor Render and verify the exact result after promotion.

For speed, perform full qualification on the candidate tree before promotion.
On the production commit, run only the smallest trustworthy non-skippable
promotion gate needed to prove that the promoted tree is the already-qualified
tree, unless repository policy or a changed tree requires the full suite.

Do not select Mode N merely because it requires no Render secret. When other
repository checks make Render's all-check behavior slow or unpredictable, use a
controlled exact-commit mode instead.

when an existing tested deploy workflow is already the least-change path.

API with `return_run_details: true` when supported, using the current GitHub API
version. Capture the returned workflow run ID and URLs immediately. When the
connected tool does not expose this parameter, correlate by exact workflow,
ref, target SHA, actor, and dispatch time rather than creating a trigger branch
or pull request.

The workflow must validate the exact authorized SHA, release-gate evidence,
portal and service identities, migration class, idempotency state, and secret
presence before making a Render request.

MODE R — OFFICIAL RENDER MCP, CLI, OR API

Use an already-authorized official Render connection when it reduces delay or
provides direct deploy IDs, logs, metrics, or exact-commit control.

- Render CLI may use `render deploys create SERVICE_ID --commit FULL_SHA --wait`.
- Render API may trigger the service with `commitId: FULL_SHA` and then poll that
  exact deploy ID.
- CLI/API specific-commit deployment does not automatically disable Render
  auto-deploy. Prevent a race by setting and recording the intended auto-deploy
  state before the request and restoring only the approved state afterward.
- Bind every call to the allow-listed workspace, portal ID, service ID,
  repository, branch, and domain.
- Never place a broad Render credential in every product repository merely for

MODE H — SERVICE-SPECIFIC DEPLOY HOOK

Use a protected service-specific hook when it is the safest available control

- Store it only in the portal repository's `production` environment.

THE OWNER-FACING OPERATING MODEL

Roger communicates with ChatGPT. ChatGPT owns orchestration. Codex is the
preferred behind-the-scenes repository implementation and review agent when it
is available through the connected ChatGPT/GitHub environment. GitHub Actions
is the deterministic qualification and evidence layer. Render is the runtime
and deployment layer. Roger must not be made to coordinate those systems.

The normal owner experience must be:

1. Roger identifies the portal and asks for the build or deployment.
2. ChatGPT discovers the connected capabilities, verifies exact identities,
   and launches or uses Codex behind the scenes for repository work when
   available.
3. Codex works in a bounded branch or task environment, edits source, runs the
   applicable local tests, and returns a concrete diff, commit, pull request,
   task reference, or equivalent evidence.
4. ChatGPT publishes or reconciles the exact repository changes and monitors
   GitHub Actions until the stable release gate passes.
5. Roger gives one explicit production authorization in ChatGPT, unless that
   authorization was already included unambiguously in his current request.
6. ChatGPT performs the exact promotion or dispatch, monitors Render, retrieves
   logs when needed, verifies the custom domain, and performs a safe automatic
   rollback when the authorization and rollback rules below permit it.
7. ChatGPT reports the exact live version, commit, deployment evidence, and one
   authoritative ZIP link.

Do not ask Roger to open Codex, write a Codex prompt, run Codex CLI, create a
branch, open or merge a pull request, trigger GitHub Actions, press a Render
deploy button, inspect logs, or perform an ordinary rollback. Those are agent
and automation responsibilities.

MAXIMUM-AUTOMATION DUTY

Before asking Roger to do anything outside ChatGPT, the builder must:

1. inspect the onboarding receipt and prior deployment evidence;
2. discover and test the available GitHub, Codex, Render MCP, Render CLI/API,
   deploy-hook, DNS, and browser/live-verification capabilities;
3. attempt every safe authenticated action the available tools actually
   support;
4. use a tested fallback when the preferred capability is unavailable;
5. prove that the remaining action is genuinely protected or impossible for
   the connected tools;
6. ask Roger for only one exact action at a time;
7. never ask Roger to paste a secret into chat;
8. immediately record the completed action so it is never requested again.

A limitation of one connector is not permission to shift the entire workflow
to Roger. Use the next safe automated path.

CODEX-FIRST, NOT CODEX-DEPENDENT

Use Codex behind the scenes whenever it is genuinely connected and useful, but
do not make the deployment system depend on Roger personally operating Codex.
The deterministic GitHub and Render path must remain reproducible if a Codex
surface is temporarily unavailable.

Preferred Codex use, in order:

1. ChatGPT-connected Codex cloud with the repository already authorized;
2. Codex GitHub integration for bounded tasks and pull-request review;
3. Codex CLI or SDK in an authenticated agent environment;
4. the official OpenAI Codex GitHub Action only when a separate OpenAI API key
   is deliberately approved, securely stored, and operationally justified.

The Codex GitHub Action is not the default merely because it exists. It adds an
API-key secret and a privileged agent step. Prefer the existing ChatGPT/Codex
GitHub connection when that can perform the work without adding another key.
When the action is justified:

- pin the action to a reviewed full commit SHA;
- use Linux and the safest supported privilege-reduction strategy;
- expose no production or Render secret to the Codex job;
- restrict triggers to trusted actors with repository write access;
- treat pull-request content, AGENTS files, screenshots, issue bodies, and
  other branch-controlled material as untrusted input;
- pass event values through validated environment variables, not direct shell
  interpolation;
- run Codex as the last step in its job or continue privileged work in a fresh
  job;
- never let Codex self-approve or directly deploy production merely because it
  wrote the code.

Create or maintain concise repository instructions for Codex, normally in a
reviewed `AGENTS.md` and deployment-specific files, so future tasks discover the
correct commands, package root, tests, forbidden files, exact-artifact rules,
health contract, and release boundaries without Roger repeating them.

When the official Render CLI is available in the agent environment, the builder
may install reviewed project-scoped Render deployment and debugging skills for
Codex. The builder, not Roger, performs and verifies that installation. Do not
install or update agent skills automatically in a privileged production job;
review and pin or record the exact installed source/version first.

Never say Codex was used unless there is actual evidence such as a task ID,
Codex run, agent log, generated branch, commit, pull request, or recorded action
output. Conversely, do not conceal Codex use. Record it in the deployment
receipt so later chats know exactly which layer performed each action.

FASTEST SAFE DEPLOYMENT DECISION TREE

Select the first compatible mode below. Do not make Roger choose among modes.

MODE A — NATIVE CI-GATED PROMOTION, DEFAULT FOR COMPATIBLE GIT-BACKED SERVICES

Use Render `After CI Checks Pass` on one explicit production branch, normally
`main`. Keep the qualified release off that branch until Roger authorizes the
exact release. Then fast-forward or otherwise promote the exact qualified tree.
Render deploys only after the stable non-skippable release gate passes. This is
the preferred recurring path because it needs no deploy-hook secret, no manual
workflow dispatch, and no Render dashboard action.

Use Render MCP, CLI, API, or live polling only for discovery, status, logs,
metrics, and post-deploy verification unless direct deployment is required.

MODE B — OFFICIAL RENDER MCP AGENT CONTROL, PREFERRED DIAGNOSTIC AND DIRECT-
CONTROL PATH WHEN ALREADY CONNECTED

Use the official hosted Render MCP connection through one-time OAuth when the
active ChatGPT/Codex environment supports it. Record the selected workspace and
allow-listed service IDs. Reverify the workspace, portal ID, service ID,
repository, branch, and domain before each deploy or environment-variable
change. Use MCP to inspect service state, trigger approved deploys, list deploy
history, retrieve logs, and diagnose failures without sending Roger to Render.

OAuth access can be broad. Do not use MCP to modify unrelated services, change
all environment variables, create infrastructure, or perform another
potentially destructive action unless Roger's current instruction authorizes
that exact action. Production secrets must not be copied into prompts, source,
logs, or receipts.

MODE C — RENDER CLI OR API EXACT-COMMIT CONTROL

Use after one approved protected credential setup when exact deploy status,
structured logs, or specific-commit control materially improves the portal.
The builder invokes the CLI/API and monitors the result. Account explicitly for
the effect of specific-commit deployment on automatic deploy settings. Do not
leave the service in a surprising auto-deploy state.

MODE D — SERVICE-SPECIFIC DEPLOY HOOK FALLBACK

Use a protected service-specific hook when native mode and official agent/API
control are unavailable or when an existing tested hook path is the safest
least-change option. Store the URL only as a GitHub `production` environment
secret. Dispatch the stable workflow directly from the default branch and
capture the returned run ID. Do not create an operations pull request merely to
start a workflow that can be dispatched directly.

MODE E — ONE EXACT OWNER STEP

Use only when all authenticated automated paths are genuinely unavailable. Give
Roger one precise protected step, verify it immediately, store a nonsecret
receipt, and return to automated operation. Never give Roger a multi-page
setup list when the next single step is enough.

ONE AUTHORIZATION, NO DUPLICATE CONFIRMATIONS

A clear current-chat instruction to deploy a named qualified release to its
canonical production domain is the production authorization. Do not ask Roger
to authorize the same deployment again merely because the workflow reached a
later stage.

Before acting, bind the authorization receipt to:

- portal ID and portal name;
- version;
- exact release ZIP SHA-256;
- candidate commit SHA;
- production-branch commit SHA when different;
- matching Git tree ID when tree-equivalent promotion is used;
- repository;
- Render service ID;
- canonical domain;
- deployment mode;
- database migration classification;
- automatic rollback permission state.

Unless Roger explicitly limits it, authorization to deploy also authorizes the
builder to perform all ordinary non-destructive follow-on actions needed to
complete that exact deployment: promotion, workflow dispatch, Render trigger,
status and log retrieval, smoke testing, evidence finalization, and safe
rollback to one distinct verified prior deploy after a material post-cutover
smoke failure. It does not authorize an irreversible migration, data restore,
billing change, domain transfer, new secret disclosure, payment activation, or
unrelated infrastructure change.

Do not perform an automatic code rollback when the release includes a
potentially irreversible or backward-incompatible database migration. Stop,
preserve the live evidence, and ask Roger for the smallest necessary decision.

ROUTINE RELEASE FAST PATH

After onboarding, ordinary releases should require no GitHub, Codex, Render,
DNS, or terminal action from Roger. The builder must execute this sequence:

1. resolve the newest authoritative artifact and current production identity;
2. use Codex behind the scenes for warranted source or deployment changes when
   available;
3. publish one coherent release branch or exact candidate commit;
4. let GitHub Actions qualify the exact tree and build the authoritative ZIP

    GitHub Release process when enabled;
13. update production truth and the onboarding/deployment receipt;

Do not rebuild the release ZIP after qualification. Do not create an operations
branch or PR merely to trigger deployment. Do not ask Roger to inspect a
routine failure that GitHub, Codex, Render MCP, CLI/API, logs, or live checks can
diagnose.

SPEED WITHOUT WEAKENING SAFETY

Optimize elapsed time by:

- running independent CI jobs in parallel;
- canceling replaceable superseded CI while queuing authorized production work;
- caching only verified package-manager download caches keyed by lockfiles;
- using `npm ci` or the exact package-manager equivalent on every clean gate;
- building and exact-testing the authoritative ZIP once;
- uploading the single ZIP directly without wrapping it again when the current
  official artifact action supports direct-file upload;
- preserving successful test evidence on the exact SHA;
- using Git tree equality to avoid rerunning the entire suite for metadata-only
  promotion commits;
- using direct workflow dispatch and the returned run ID;
- using native CI-gated deployment where compatible;
- using Render MCP or CLI/API for immediate deploy status and logs;
- treating already-live and already-running identical targets as successful
  monitored no-ops;
- measuring per-portal build and deployment duration and setting evidence-based
  timeouts.

Never gain speed by weakening the release gate, skipping exact-artifact tests,
using mutable dependencies, exposing secrets, bypassing required migration
review, accepting a soft 404, or declaring success before the canonical domain
proves the exact live version and commit.

RESEARCH BASIS AND SEVENTH-PASS IMPROVEMENTS

This seventh pass preserves every useful rule from the sixth pass and adds a controlling Codex-first, Roger-zero-touch execution core after a fresh review of current official OpenAI Codex, GitHub Actions, workflow-dispatch, workflow-concurrency, reusable-workflow, ruleset, immutable-release, artifact-upload, Render deploy, Blueprint, health-check, rollback, CLI, MCP, coding-agent, and image-deployment documentation as of August 1, 2026. The implementation must re-check current official documentation when it is actually installed because platform behavior can change.

The most important research-backed improvements incorporated here are:

1. Use one exact qualified source tree and one authoritative release artifact from qualification through production, tag, Release, and rollback evidence. Prefer a fast-forward promotion of the already-qualified release SHA to `main` when repository rules and connected tools permit it. When repository policy creates a new merge or rebase SHA, compare Git tree object IDs: an identical tree may use the lightweight promotion-proof gate, while a changed tree requires full qualification.
2. Separate shared CI from production control. GitHub reusable workflows are excellent for central CI. Mode N normally needs no production secret and may use only a tiny stable production gate. Secret-bearing modes must keep a tiny portal-local workflow that references the portal’s `production` environment and invokes a centrally maintained composite action or checked-in script pinned to an exact SHA, because environment secrets cannot be cleanly passed through `workflow_call` in the ordinary caller job.
3. Choose the least-friction deployment mode already available. For a Git-backed service whose production branch and CI gate are trustworthy, the new preferred recurring path is Render’s native `After CI Checks Pass` auto-deploy mode: Roger authorizes promotion in chat, ChatGPT advances the exact qualified commit to the linked production branch, Render deploys only after CI passes, and no per-portal Render deploy secret is required. A service-specific deploy hook remains the default controlled fallback when exact manual dispatch, self-contained polling, or an existing working setup is more important. A Render API key, official Render MCP connection, or pinned Render CLI is an optional portfolio optimization, not a reason to make Roger redo a safe working setup.
4. Use Render’s own `RENDER_GIT_COMMIT` runtime value for exact live commit identity whenever available. Do not invent or manually maintain a second commit variable when Render already supplies the authoritative deployed SHA.
5. Use a preflight dry run before the first live deployment of each portal. It must verify configuration, selected deployment mode, conditional secret presence without revealing values, service identity, linked branch and auto-deploy trigger, release-gate evidence, health behavior, custom domain, and smoke manifest without triggering Render.
6. Keep a machine-readable one-time onboarding receipt so future chats can see which protected setup steps are already complete and never ask Roger to repeat them.
7. Use dependency caching only for package-manager download caches keyed by the lockfile; never cache `node_modules` or allow a cache hit to replace `npm ci`.
8. Validate `render.yaml` with the official Render CLI when used. Do not automatically Blueprint-sync an existing service until configuration drift and ownership effects are reviewed.
9. Align production waiting with Render’s deployment model. Render may spend up to approximately fifteen minutes waiting for new instances to pass health checks, so a deployment workflow must not declare failure prematurely. API or CLI mode should use direct deploy status; hook mode should use bounded health polling long enough to distinguish a normal build from a real timeout.
10. Use GitHub and Render concurrency deliberately. Production requests must not overlap, silently replace one another, or trigger competing Render deploys. Revalidate the requested SHA immediately before deployment so a queued but superseded request becomes a safe no-op or a blocked request rather than an obsolete production change.
11. Make setup plan-aware. Do not assume private-repository environment reviewers are available on Roger’s GitHub plan. Chat authorization remains the owner approval; GitHub environments are used primarily for secret scope, branch restriction, history, and isolation.
12. Preserve a simple fallback. If a central shared workflow or composite action is not yet available, vendor the tested deployment kit locally. Do not delay a qualified portal merely to perfect portfolio architecture.
13. Prefer direct `workflow_dispatch` through the GitHub REST API whenever the connected tool supports it. GitHub now returns the workflow run ID and run URLs in the dispatch response, so the builder should capture that run immediately and monitor it directly. Do not create an operations branch or pull request merely to trigger a workflow that can be dispatched in one authenticated request.
14. Build and qualify the authoritative release ZIP once. Upload that already-tested ZIP as one immutable GitHub Actions artifact, record its artifact ID, URL, digest, release SHA-256, candidate commit, tree object ID, workflow run ID, and version in a machine-readable release manifest, and reuse the exact artifact for the GitHub Release after production verification. Do not rebuild the ZIP after deployment.
15. Treat Git tree identity as exact source-tree identity. If a pull-request merge, rebase, or protected promotion creates a different commit SHA but `candidate^{tree}` and `main^{tree}` are identical, use a lightweight promotion-proof gate instead of rerunning the entire expensive suite solely because commit metadata changed. Deploy the exact current `main` commit while preserving the qualified candidate, matching tree ID, and artifact manifest as evidence. If tree IDs differ, rerun the complete gate.
16. Make artifact-attestation use plan-aware. GitHub artifact attestations for private repositories require GitHub Enterprise Cloud. On other private-repository plans, do not grant unused OIDC or attestation permissions and do not treat the unavailable feature as a blocker; exact SHA-256, inventory, immutable workflow artifact, two-extraction testing, and deterministic rebuild remain controlling.
17. Use production concurrency with `queue: max` and without `cancel-in-progress: true` so authorized production requests queue instead of replacing one another. Revalidate the target immediately before deployment because queued execution order is not an authorization guarantee and Render’s Wait policy can skip intermediate deploys.
18. Make dependency-cache behavior explicit. Current `actions/setup-node` can enable npm caching automatically when package-manager metadata is present. For ordinary CI, explicitly declare the intended lockfile-keyed download cache and still run `npm ci`; for privileged production jobs that do not install dependencies, disable unnecessary automatic package-manager caching.
19. Upload a prebuilt ZIP as a single file without unnecessary double-archiving when the current official artifact action supports it. Preserve the release ZIP’s own SHA-256 as authoritative even when GitHub also reports an artifact digest.
20. Keep `workflow_dispatch` deployment files on the default branch, because GitHub only accepts manual dispatch for workflows present there. Dispatch the trusted workflow definition from `main`, pass the target SHA as a validated input, and never execute a production workflow definition taken from an untrusted release branch.
21. Use Render CLI mode as the fastest diagnostic mode after one approved API-key setup: pin the reviewed CLI, run `deploys create SERVICE_ID --commit SHA --wait --confirm -o json`, capture the deploy object, and stream failure information. Continue to prefer a service-specific hook when avoiding the broader API credential is more important than richer status.
22. Account for Render’s exact hook response behavior. HTTP 200 means a deploy started and normally includes a deploy ID; HTTP 202 means another deploy is in progress and the new request is queued without a deploy ID. Both require final live verification. A hook acceptance response is never production success.
23. Base hook-mode timeout on observed build duration plus Render’s documented new-instance health window, with a reasonable margin. Do not declare failure during a normal build, but also do not allow an unbounded poll. Record p50 and p95 deployment duration per portal and tighten the timeout after evidence accumulates.
24. Make the portfolio fast lane optional and measurable. After several portals prove the same local pattern, a central deployment repository may hold one protected Render API key and one read-only GitHub App or equivalent credential, while product repositories contain no Render secret. Adopt this only when the central allow-list, cross-repository release-gate verification, exact target binding, failure isolation, audit, and rollback are complete and the measured reduction in Roger’s setup work exceeds the added security and maintenance burden.

25. Add a native zero-secret deployment target. When Render is linked to the portal repository and set to `After CI Checks Pass`, explicit chat authorization can be enforced by withholding promotion to the linked production branch until Roger approves. This normally removes the recurring deploy-hook secret, the production dispatch workflow, and one entire class of setup confusion.
26. Treat Render’s CI-result semantics as a safety requirement. Render currently counts GitHub check conclusions of `success`, `neutral`, and `skipped` as passing and refuses to deploy when it detects zero checks or any failure. Therefore every native-deploy portal must expose one stable, non-skippable, always-created production release gate that explicitly fails when any mandatory prerequisite failed, was canceled, or was unexpectedly skipped. Never rely on a collection of optional checks whose skipped states could be misread as approval.
27. Never create a post-deploy GitHub check that can deadlock Render’s `After CI Checks Pass` trigger by waiting for a deployment that Render is itself waiting to start. Post-deploy verification must run through ChatGPT’s Render tools, a separately dispatched verifier after Render starts, a signed Render webhook on an eligible plan, or another event path that is not part of the pre-deploy check set.
28. Use the official Render MCP server or another official Render connector when the receiving ChatGPT environment actually supports it and Roger completes one-time authorization. This can let ChatGPT create services, trigger deploys, inspect deploy history, retrieve logs, and inspect metrics without asking Roger to operate Render. Because current Render OAuth and API credentials are broadly scoped, bind every operation to an allow-listed workspace, portal ID, service ID, repository, branch, and domain; confirm destructive operations; and never require Roger to operate Codex merely because Render’s documentation lists it. ChatGPT should use Codex behind the scenes when it is actually connected and useful.
29. Prefer native Render Git integration for recurring releases and reserve exact-commit manual deploys for controlled exceptions. Render documents that dashboard and deploy-hook specific-commit deployments disable auto-deploys, while CLI and API specific-commit deployments do not. The workflow must record and verify the resulting auto-deploy state instead of assuming all methods behave the same.
30. Use Render’s `Wait` overlapping-deploy policy for the portfolio unless a documented incident-response need justifies `Override`. Render may skip intermediate waiting deploys, so the production path must revalidate the final queued target and must never assume every queued commit will deploy.
31. Make repository changes, not dashboard clicks, the recurring authorization boundary. The safest fast native pattern is: qualified release SHA -> Roger’s exact chat authorization -> non-forced promotion to the linked production branch -> one non-skippable production gate -> Render `checksPass` auto-deploy -> direct Render/live verification. If promotion changes the commit SHA, apply the existing tree-equivalence rule.
32. Use build filters and a root directory only to avoid deployments for proven nonruntime changes. Never ignore package manifests, lockfiles, migration files, runtime configuration, deployment scripts, health logic, public assets, source data, or `render.yaml`. Build filters affect auto-deploys and previews, not manual deploys.
33. Prefer Render’s native rollback to a retained successful deploy when direct API, CLI, MCP, or dashboard capability is available because it can reuse the prior build artifact and complete faster than rebuilding an old commit. Record that API rollback does not disable auto-deploys, while dashboard rollback does; quarantine or repair the failed production branch before re-enabling ordinary promotion.
34. Add a plan-aware event-driven completion path. On Render Pro or higher, a signed `deploy_ended` webhook can trigger final smoke and evidence without long polling. Validate Standard Webhooks signatures, reject stale timestamps, deduplicate with the Render event ID, bind the service ID to the portal registry, respond within the documented deadline, and preserve bounded polling as the fallback.
35. Record production in GitHub’s deployment model as well as in portal evidence. A production job or verifier should use the `production` environment and environment URL, and may create deployment status records with the exact SHA and canonical URL when permissions allow. This makes the live state visible without creating a second source of truth.
36. Make one-time portfolio setup organization-aware. Where Roger’s repositories are in a GitHub organization and the current plan supports it, use organization workflow templates, reusable workflows, selected-repository variables, selected-repository secrets, and organization rulesets to remove repetitive setup. Where the plan or account structure does not support them, use the equivalent repository-local configuration without blocking deployment.
37. Use the current official `actions/upload-artifact` direct single-file mode when available (`archive: false`) so an already-qualified ZIP is uploaded as the exact file instead of being wrapped in another archive. Pin the reviewed action to a full commit SHA, verify the downloaded file’s own SHA-256, and retain deterministic local archive identity as controlling truth.
38. Add Dependabot maintenance for GitHub Actions and reusable workflows, but never auto-merge a workflow-pin update into production merely because it is newer. Each pin update must run the deployment fixture suite and portal release gate; the comment beside a full SHA should retain the reviewed release tag for human readability.
39. Avoid privileged `workflow_run` and `pull_request_target` designs unless necessary. When used, do not check out or execute untrusted head code, do not trust artifacts from untrusted runs, use minimal permissions, and bind every event to the exact authorized production branch and SHA.
40. Make the onboarding receipt describe the selected target explicitly: `native_checks_pass`, `service_hook`, `render_mcp`, `render_api_cli`, `prebuilt_image_digest`, or `central_deployer`. Future chats must inspect that receipt before proposing a different mode or asking Roger to repeat setup.

41. Establish one default Roger-optimized golden path instead of making Roger choose among deployment architectures. The builder must inspect the existing portal, select the least-friction compatible target, explain only the chosen result, and record rejected modes in evidence. Ordinary onboarding should end with `readyForHandsOff: true` or an exact list of remaining protected owner actions.
42. Enforce an owner-interruption budget. After onboarding, Roger’s recurring work should be limited to describing changes, explicitly authorizing the exact qualified release in chat, and reviewing the live site. A portal should not require recurring GitHub, Render, DNS, terminal, or secret-management clicks. When a protected one-time action is unavoidable, provide exactly one UI step at a time and never ask Roger to paste a secret into chat.
43. Add a deterministic deployment-doctor command that performs non-destructive discovery and preflight in one run. It should identify repository, default and production branches, release-gate state, Render source type, service ID, auto-deploy state, overlapping-deploy policy, custom domain, health path, selected mode, required secret names without values, current live version and commit, rollback identity, and remaining owner actions. The doctor must produce both human-readable output and a machine-readable receipt.
44. Enable GitHub immutable releases when the repository and plan support them. Create the release as a draft, attach every final asset, verify hashes, and publish only after production verification. Publication should lock the tag and assets. Never publish an incomplete immutable release or depend on editing it later.
45. Add a portable repository ruleset file and import path when current GitHub plan and permissions support it. The ruleset should protect the production branch and release tags, block deletion and force-push, require the stable production gate, and preserve a documented administrator recovery path. Use a repository-local fallback when ruleset import is unavailable.
46. Treat Render’s zero-downtime failure model as an explicit state machine. A build, pre-deploy, startup, or new-instance health failure before traffic cutover normally leaves the prior successful deploy serving traffic and requires no rollback request. Only a distinct deploy that became live and then failed independent production smoke is eligible for explicit rollback.
47. Treat Render auto-deploy state as controlled production data. Record it before and after every exceptional exact-commit deployment or rollback. Dashboard and deploy-hook specific-commit deployments disable auto-deploy; CLI and API specific-commit deployments do not; dashboard rollback disables it while API rollback does not. Never assume the previous state survived.
48. Prevent branch-head and exact-commit races. In native mode, the deployed SHA must be the linked production-branch head. In manual exact-commit mode, either the linked branch must already point to the same SHA or auto-deploy must be intentionally off or otherwise controlled so a newer branch-head deploy cannot immediately replace the authorized target.
49. Prefer direct Render deploy status over public polling whenever an official connector, MCP, CLI, API, or returned deploy ID is available. Use the live health and smoke contract to prove traffic cutover and application behavior, not as a substitute for available build status. Poll only when direct status is unavailable, and use bounded backoff.
50. Correlate every manual production run without creating a branch or pull request. Use a stable default-branch `workflow_dispatch`, typed inputs, a descriptive `run-name`, the returned workflow run ID and URLs, the exact target SHA, and a nonsecret authorization receipt. Re-running a failed job must remain bound to the original trusted workflow revision and exact target.
51. Add an optional prebuilt immutable-image acceleration target for portals whose measured Render source builds are materially slow, duplicated, or insufficiently reproducible. Build and test one `linux/amd64` image in GitHub CI, push it to an approved registry, record the immutable image digest, and deploy that digest to an image-backed Render service. Do not adopt this target merely because containers are fashionable.
52. For image-backed deployment, use digests rather than mutable tags for production and rollback, retain every currently deployable and rollback digest in the registry, verify Render’s registry credentials, and bind the image digest to the source commit, release ZIP, SBOM or dependency evidence when available, and production smoke. Never delete a rollback image merely to save storage.
53. Keep native Git-backed deployment as the default for portals that already deploy quickly and reliably. Move to the image-backed acceleration target only after a measured comparison shows a material benefit that exceeds the added registry, credential, image-retention, scanning, and service-conversion burden.
54. Never clear Render’s build cache by default. Use `clear_cache` only for a diagnosed cache problem, build-system change, or stale-asset incident, record why it was required, and compare the resulting deploy duration and behavior.
55. After a rollback, quarantine the failed production state before ordinary automation resumes. Prevent the broken branch head, mutable image tag, or still-enabled auto-deploy from immediately redeploying the failed release. Restore a known-good production pointer or intentionally hold auto-deploy off until a repaired qualified release is authorized.
56. Measure Roger-facing efficiency as a release quality attribute. Record owner manual actions, setup actions, deployment duration, time spent waiting for status, duplicate requests avoided, no-op deploys, failed deployments, automatic pre-cutover protection, rollbacks, and recovery time. A more centralized design is warranted only when it measurably reduces Roger’s work without weakening isolation, truth, or recovery.
57. Use the current Render Blueprint control field `autoDeployTrigger`; do not introduce the deprecated `autoDeploy` field into a new standard. For a new Git-backed portal, prefer `checksPass` when native CI-gated promotion is selected and `off` for controlled exact-commit modes. For an existing service, never assume a Blueprint sync is harmless: first snapshot current settings, because Blueprint synchronization can replace existing build-filter configuration and other managed fields.
58. Separate Render's platform health gate from the stricter application smoke contract. Render's HTTP health check accepts a `2xx` or `3xx` response within five seconds and can wait up to fifteen minutes for all new instances to become healthy. The portal's deployment health endpoint should be stricter: normally exact `200`, no redirect, exact portal/version/commit identity, required datastore readiness, and no dependency that is not operation-critical.
59. Treat Render rollback as an application-build rollback, not a universal infrastructure or data rollback. Before rollback, verify the target deploy's retained artifact and migration compatibility. After rollback, re-verify current domains, instance type, persistent disks, environment groups, and all other current service settings that Render does not fully restore from the old deploy.
60. Strengthen database safety around `preDeployCommand`. A pre-deploy failure normally leaves the prior application serving traffic, but the command might have created partial database side effects. Require idempotent migrations, transaction use where supported, a migration ledger, backward-compatible expand-and-contract sequencing, retry tests, and an explicit rule that rolling back code does not roll back schema or data.

Preserve a repository-local fallback when the plan or ownership model does not support this.

Where available, first use evaluate mode, then restrict production `workflow_dispatch` to Roger, trusted maintainers, or the approved GitHub App and permit only the required events. Because the feature remains subject to platform change, never block a safe portal deployment merely because it is unavailable.

A private shared repository can accelerate onboarding, but outside collaborators on consuming repositories may indirectly view shared-workflow logs or content. Never place Render credentials, portal secrets, confidential evidence, or private user data in the shared workflow repository or its logs.

Do not keep an obsolete action major merely from habit, and do not recompress an archive that is already exact-tested.

Private-repository build attestations remain plan-aware, while publishing an immutable GitHub Release automatically creates release-level integrity evidence. 2B. FOUR OPERATING TARGETS — NATIVE ZERO-SECRET, PORTAL QUICK PATH, IMMUTABLE IMAGE ACCELERATION, AND PORTFOLIO FAST LANE

Use one explicit operating target at a time. Do not mix their assumptions accidentally.

TARGET N — NATIVE CI-GATED ZERO-SECRET PROMOTION

Use as the preferred recurring path when all of the following are true:

- the service is Git-backed and linked to the correct repository and production branch;
- Render can use `After CI Checks Pass`;
- the portal has one stable, non-skippable production release gate;
- Roger’s explicit chat authorization can be enforced by withholding branch promotion until approval;
- the receiving ChatGPT can promote or merge the exact qualified commit and then monitor Render or the live health contract;
- no deployment-specific secret is needed for ordinary releases.

One-time setup:

- link the correct GitHub repository and production branch in Render;
- set Auto-Deploy to `After CI Checks Pass` or `autoDeployTrigger: checksPass`;
- configure the health-check path;
- verify the workspace overlapping-deploy policy;
- configure safe build filters only when warranted;
- record the service ID, branch, domain, health path, and auto-deploy state in the onboarding receipt.

Normal recurring path:

- exact qualification on `release/<version>`;
- Roger authorizes that exact release in chat;
- ChatGPT non-forced fast-forwards the linked production branch to the exact qualified SHA, or produces a tree-equivalent promotion proof when repository policy creates a different commit;
- the non-skippable production gate runs;
- Render detects the passing checks and deploys;
- ChatGPT monitors Render directly when possible and verifies the live version, commit, domain, routes, 404s, and critical services;
- no deploy-hook secret and no recurring Render dashboard action.

This is normally the fastest and easiest target for Roger.

TARGET Q — CONTROLLED PORTAL QUICK PATH

Use when an exact manual deploy is required, a hook is already installed, native auto-deploy cannot enforce the desired authorization boundary, or the portal needs one self-contained workflow that requests, waits, smokes, and conditionally rolls back.

One-time protected owner action when tools cannot perform it:

- place `RENDER_DEPLOY_HOOK_URL` in the portal repository’s `production` environment.

Normal recurring path:

- direct dispatch;
- exact target validation;
- hook request with `ref=FULL_SHA`;
- bounded live polling;
- smoke;
- safe rollback only when warranted.

This target has a service-specific credential and a small blast radius. A specific-commit hook deploy disables Render auto-deploys, so record that state and do not later assume native auto-deploy remains enabled.

TARGET F — PORTFOLIO FAST LANE

Use only after the native or quick path is proven across enough portals to justify centralization.

One-time portfolio setup may include:

- an official Render MCP connection in a compatible ChatGPT environment, or a private central deployment repository;
- one protected `RENDER_API_KEY` accessible only in the authorized control plane;
- one GitHub App installation credential or equivalently limited read credential for release-gate and commit verification across an explicit selected-repository allow-list;
- a checked-in registry mapping immutable portal IDs to repository, Render service ID, canonical domain, production branch, health contract, and smoke manifest;
- direct dispatch or direct MCP action;
- portal-specific authorization and target SHA as inputs;
- exact cross-repository qualification verification before any Render request.

Product repositories should not receive the central Render API key unless a selected-repository organization secret is the explicitly approved design. The central control plane must reject every repository, service, workspace, branch, domain, or commit not present in its allow-list. A target repository must remain independently buildable and recoverable through Target N or Target Q if the central system is unavailable.

TARGET I — PREBUILT IMMUTABLE-IMAGE ACCELERATION

Use only when measured source-based Render builds are materially slow, duplicate work already completed in GitHub CI, or reproducible runtime packaging creates a clear operational benefit.

One-time setup may include:

- a reviewed multi-stage Dockerfile and `.dockerignore`;
- a GitHub Actions image-build job pinned to reviewed action SHAs;
- an approved registry, normally GitHub Container Registry when repository and package access can be controlled safely;
- `linux/amd64` image output compatible with Render;
- one private-image credential in Render when the image is private;
- an image-backed Render service or approved conversion plan;
- a service-specific deploy hook, CLI, API, or MCP path capable of deploying an exact image digest;
- image-retention and rollback rules.

Normal recurring path:

- build, test, and scan one image in GitHub CI;
- push it once;
- record the exact digest and source commit;
- Roger authorizes the exact release and digest in chat;
- deploy the digest, never a mutable production tag;
- verify direct Render status, health, commit or build identity, routes, and smoke;
- retain the prior known-good digest for rollback.

Do not use Target I when it adds a recurring owner step, makes local development or emergency recovery materially harder, loses a working native preview workflow without replacement, or saves too little time to justify registry and credential maintenance.

Selection rule:

1. Use Target N when it is safe and supported because it removes the per-portal deployment secret and recurring trigger step.
2. Preserve Target Q when it is already working or when closed-loop manual deployment provides a material safety benefit.
3. Evaluate Target I only when measured source-build time or reproducibility evidence shows a material benefit and the registry path can remain hands-off for Roger.
4. Adopt Target F only when it measurably removes repeated setup and monitoring work across multiple portals without creating a fragile network-critical dependency.
5. Never force Roger to redo a working setup merely to conform to a newer mode.
6. Retain a tested rollback and local fallback.

1. a very small caller workflow for shared CI, pinned to an exact full commit SHA;
2. for Mode N, a stable non-skippable portal-local production gate and no secret-bearing deployment wrapper; or
3. for Mode H, C, or P, a very small portal-local production workflow that references `environment: production` and invokes the central composite action or checked-in script pinned to an exact full commit SHA.

This split is deliberate. Shared CI centralizes nonsecret logic. Mode N keeps the recurring path secret-free. Secret-bearing modes use the local production wrapper to preserve reliable access to environment secrets and environment history.

Benefits:

- one place to improve security and deployment behavior;
- fewer duplicated files;
- faster onboarding;
- less version drift;
- consistent evidence and rollback behavior;
- no need to edit every portal when ordinary product versions change;
- a controlled upgrade path by changing one pinned central SHA in a tested deployment-standardization release.

Do not point callers or composite actions to a floating branch such as `main`. Pin to a reviewed full commit SHA.

Configure the private shared repository’s Actions access so only authorized repositories owned by Roger’s organization or account can consume it. Review the outside-collaborator implications documented by GitHub before broadening access.

Where an organization `.github` repository is available, create workflow templates so a new portal can install the small CI caller, the selected mode’s production gate or wrapper, and starter configuration quickly. Templates are onboarding aids; exact pinned shared workflows and portal-specific configuration remain authoritative.

If the repositories are organization-owned and the current plan supports it, use one nonsecret repository custom property such as `legal-micro-portal=true` to target shared rulesets, immutable-release policy, selected-repository variables, workflow templates, and approved workflow-execution protections. Apply those policies in evaluate or dry-run mode first where supported, record the result, and activate them only after they do not block the proven release path.

A shared workflow repository must contain no portal or Render secrets. Treat every shared action and reusable workflow as code that consuming-repository collaborators may indirectly observe through logs. Pin every caller to a reviewed full commit SHA, declare minimal permissions, and keep the secret-bearing production boundary portal-local unless a separately approved central deployer has complete isolation and auditing.

If private workflow sharing is unavailable or not yet configured, vendor the stable generic workflows and scripts into the portal repository. Do not delay a safe portal release merely to build the central repository.

Do not automatically mutate other product repositories. Each portal adopts a shared-standard upgrade through its own exact-tested release. A central deployment standard may be improved once, but every caller-pin update remains an explicit portal-local change.

===============================================================================
7A. SUPPORTED DEPLOYMENT OPERATING MODES
===============================================================================

MODE N — NATIVE RENDER `AFTER CI CHECKS PASS`

Use for a Git-backed service when branch promotion is the authorization boundary.

Requires:

- Render linked to the correct production branch;
- `autoDeployTrigger: checksPass` or the equivalent dashboard setting;
- at least one detected GitHub check;
- one stable production gate that always runs and explicitly fails on any mandatory failure, cancellation, or unexpected skip;
- direct Render or live monitoring after promotion.

Advantages:

- zero per-portal deployment secret;
- no recurring dispatch step;
- exact Git commit remains the deployment source;
- Render does not deploy when zero checks are detected or any check fails;
- Roger’s recurring action is only the explicit chat authorization.

Do not use this mode with a gate that may be skipped. Render currently treats `success`, `neutral`, and `skipped` as passing conclusions.

MODE H — SERVICE-SPECIFIC DEPLOY HOOK

Use when a hook already exists or a self-contained manual-deployment workflow is materially safer.

Requires:

- one portal environment secret: `RENDER_DEPLOY_HOOK_URL`;
- no account-wide API key;
- live health polling for final verification.

A hook deployment of a specific `ref` disables Render auto-deploys. Record that effect and do not silently switch between native and hook modes.

MODE M — OFFICIAL RENDER MCP OR CONNECTOR

Use only when the receiving ChatGPT actually exposes the official Render tools and Roger has completed one-time authorization.

Advantages:

- direct service and deploy discovery;
- direct deploy history and status;
- direct logs and metrics;
- fewer GitHub secret and workflow steps;
- potential service creation and environment repair by ChatGPT.

Controls:

- set and verify the intended workspace;
- bind portal ID to immutable service ID, repository, production branch, and domain;
- retrieve current service details before every destructive action;
- do not modify environment variables, scaling, billing, databases, or domains during an ordinary release;
- treat broad OAuth or API-key scope as a high-authority credential;
- require exact product-scoped chat authorization for deployment and rollback.

MODE C — RENDER CLI OR API

Use when an approved `RENDER_API_KEY` and `RENDER_SERVICE_ID` already exist or when Roger explicitly chooses the portfolio optimization.

Advantages:

- direct deployment status;
- faster failure diagnosis;
- deploy logs through the official CLI;
- precise deploy IDs;
- API rollback to retained build artifacts.

This mode has a broader secret blast radius and must not be adopted casually. A CLI or API specific-commit deployment does not automatically disable auto-deploys, so verify or deliberately update the service state.

MODE P — CENTRAL PORTFOLIO DEPLOYER

Use only after a separate security and operations audit when connected tools can reliably create authenticated cross-repository requests. A central deployment repository may hold the API key and a nonsecret service registry, leaving product repositories with no Render secret.

Do not make this the default merely to create architecture. It is warranted only when it materially reduces repeated setup across many portals and preserves exact target authorization, least privilege, independent portal operation, audit, failure isolation, and rollback.

Selection rule:

Use the simplest already-operational mode. Prefer Mode N for new compatible portals, preserve Mode H when already working, use Mode M when officially connected and tightly bound, and adopt Mode C or P only when the measured reduction in Roger’s work exceeds the new security and maintenance burden.

A central portfolio deployer is not accepted until it proves all of the following with synthetic and live-pilot evidence:

- an immutable allow-list maps portal ID to repository, service ID, production branch, and canonical domain;
- the caller cannot substitute another repository, service, workspace, branch, or domain;
- the exact target commit is on the authorized portal’s production branch;
- the target’s release gate or tree-equivalent promotion proof is independently verified across repositories;
- the central GitHub credential is read-only for product repositories;
- the Render credential is available only to the central production job;
- production requests queue and revalidate before execution;
- each portal’s failure cannot corrupt another portal’s state;
- local native or quick-path fallback remains tested;
- the central setup actually reduces Roger’s repeated protected steps.

7B. NATIVE CI-GATED AUTO-DEPLOY CONTRACT
===============================================================================

For Mode N, implement all of the following:

1. Link Render to one explicit production branch, normally `main` unless a dedicated `production` branch creates a material safety or workflow benefit.
2. Set Render Auto-Deploy to `After CI Checks Pass`.
3. Keep the exact qualified release away from the linked branch until Roger authorizes that exact version and SHA in the current chat.
4. Promote with a non-forced fast-forward whenever possible.
5. If repository policy creates a new commit SHA, compare Git tree IDs and use the existing promotion-proof rule.
6. Ensure a stable production gate is created for every production-branch update.
7. Make the production gate `if: always()` or its equivalent and explicitly inspect all mandatory prerequisite results. It must fail when a required job failed, was canceled, or was unexpectedly skipped.
8. Do not include a post-deploy polling job in the check set Render is waiting on.
9. Configure Render’s HTTP health path and allow the documented new-instance readiness window.
10. Set or verify the Render workspace overlapping-deploy policy. Prefer `Wait`.
11. After the gate passes, monitor Render through an official connector, MCP, CLI/API, Render event, or bounded live polling.
12. Classify `already_live` before waiting. If the live health endpoint already reports the exact version and commit, run smoke and record a no-op success.
13. Run the full production smoke suite after the exact commit becomes live.
14. If smoke fails after traffic cutover, use a distinct known-good rollback deploy when safe or restore the production branch to the known-good source under the migration rules.
15. Record the actual Render deploy ID when tools expose it; otherwise record the exact live version, commit, first-seen time, and evidence source.
16. Keep native mode disabled for a portal whose service deploys from a public Git URL, prebuilt image without appropriate automation, or another source that cannot use CI-gated Git auto-deploys.

8. GITHUB ACTION SECURITY AND SPEED
===============================================================================

Apply these rules:

1. Pin every third-party action to a full commit SHA. A version comment may be added for readability.
2. Use the least workflow permissions required.
3. Use `contents: read` for CI unless a job truly creates a tag or Release.
4. Give `contents: write` only to the post-production release job.
5. Do not expose production secrets to pull-request jobs.
6. Do not run untrusted fork code with production secrets.
7. Use concurrency to prevent overlapping production deploys.
8. Use `cancel-in-progress: true` for replaceable CI runs.
9. Use `cancel-in-progress: false` for production deploys.
10. Use lockfiles and `npm ci`, not an unconstrained install.
11. Use `actions/setup-node` package-manager caching only when it is keyed by the lockfile; cache the download store, never `node_modules`, and still run `npm ci`.
12. Use exact Node.js and npm versions in CI and Render.
13. Add sensible `timeout-minutes` to every job so a hung dependency, database, or network call fails clearly.
14. Keep artifacts for a short, purposeful retention period.
15. Do not package `.git`, `node_modules`, caches, coverage, logs, secrets, runtime data, or temporary files.
16. Use only current official actions and verify their source repositories before pinning.
17. Generate GitHub artifact attestations for the exact release ZIP when the repository plan and permissions support them; treat this as extra provenance, not a replacement for SHA-256, inventory, or two-extraction testing.
18. Do not grant `id-token: write`, `attestations: write`, `packages: write`, or any other permission unless the exact job needs it.
19. Make production concurrency unique to the portal, such as `production-${{ github.repository }}`, so workflows in separate repositories cannot interfere.
20. Where GitHub’s queued concurrency is available, use `queue: max` for authorized production requests and revalidate the target SHA immediately before deploying. Otherwise ensure a new pending request cannot silently discard a previously authorized one.
21. Because current `actions/setup-node` can automatically enable npm cache when package-manager metadata is present, explicitly configure `cache: npm` and `cache-dependency-path` for ordinary CI or explicitly set `package-manager-cache: false` when caching is not intended. Never depend on an implicit default for a production-security decision.
22. When uploading the already-zipped exact release, prefer the current official artifact action’s single-file non-archived mode where supported so the downloaded file is the same ZIP rather than a ZIP wrapped inside another ZIP. Always verify the downloaded asset’s own SHA-256.
23. Do not enable artifact-attestation permissions for a private repository unless the current GitHub plan supports private-repository attestations. Lack of that optional feature is not a release failure.
24. Restrict manual production dispatch to maintainers or trusted actors when current GitHub workflow-execution protections are available, without making Roger perform repeated approvals.
25. For native Render mode, make the production aggregator check stable in name and always created; do not allow path filtering to suppress the only check Render relies on.
26. Treat `neutral` and `skipped` as nonblocking only because Render does; the aggregator must translate any unexpected skipped mandatory job into a failure.
27. Pass untrusted event values through validated inputs or intermediate environment variables, never direct shell interpolation.
28. Avoid `pull_request_target` and privileged `workflow_run` execution of untrusted code or artifacts.
29. Enable Dependabot updates for GitHub Actions and reusable workflows, but require the deployment fixture suite before merging a pin update.
30. When plan and account structure permit, use an organization ruleset or imported repository ruleset to protect the production branch consistently; keep a repository-local fallback.
31. Use GitHub deployment environments and environment URLs for audit even when Mode N has no environment secret.

===============================================================================
9. RELEASE CI WORKFLOW
===============================================================================

Create a version-agnostic release CI workflow triggered by:

- pull requests targeting the repository’s integration or production branch, normally `main`;
- pushes to `release/**`;
- pushes to the Render-linked production branch;
- manual dispatch when useful.

Resolve one exact candidate commit:

- pull request head SHA for a PR;
- the pushed SHA otherwise.

Every job must check out that exact SHA.


The candidate SHA should remain the same through qualification, promotion, deployment, production tag, and GitHub Release whenever practical.

Preferred promotion path after `release-gate` passes and only after Roger authorizes the exact deployment when the target branch is Render-linked:

1. verify the linked production branch, normally `main`, is still an ancestor of the qualified release SHA;
2. fast-forward that branch to the exact SHA with `force: false` or the equivalent protected operation;
3. preserve the existing check runs attached to the same SHA;
4. allow Mode N to deploy that exact SHA through CI-gated native auto-deploy, or invoke the selected controlled mode without rebuilding or creating a merge-only commit.

This avoids a second full qualification caused solely by a changed merge SHA.

Fallback path after authorization:

- merge through the required pull-request method;
- resolve the resulting exact linked-production-branch SHA;
- compare tree identity and use the promotion-proof rule when exact;
- rerun the complete release gate for that resulting SHA before deployment when the tree changed.

Never treat tests on a different PR-head SHA as proof of the merge commit.

Export a clean source tree with `git archive` before source-integrity and exact-artifact checks so `.git` metadata and unrelated workspace residue cannot affect the result.

Use parallel jobs where safe. Begin with a deterministic changed-file classifier, but allow it to skip work only when the skipped work is provably irrelevant. A release candidate that changes executable source, dependencies, workflows, deployment configuration, routes, data, migrations, forms, profiles, or release evidence must run the complete applicable gate. Documentation-only optimization must never weaken exact-artifact or version-truth checks for a delivered product ZIP.

Use parallel jobs where safe:

A. SOURCE INTEGRITY

- verify checked-out SHA;
- verify package version and deployment configuration;
- verify self-excluding inventory;
- run syntax checks;
- parse JSON, YAML, XML, and other structured files;
- scan for forbidden packaged files and obvious secret patterns;
- validate routes, links, profile data, source data, and release records;
- verify no stale current-version claims;
- verify the health and 404 contracts in source.

B. APPLICATION AND RUNTIME TESTS

- start the correct database service where required;
- install exact dependencies with `npm ci` or the equivalent;
- run the complete current suite;
- run runtime/server tests;
- run migration tests;
- run authorization and fail-closed tests;
- run the current vulnerability audit at the agreed severity threshold;
- distinguish registry or infrastructure failure from a source defect.

C. FULL PLATFORM STATIC AUDIT

- public routes;
- protected routes;
- accessibility source checks;
- bilingual or multilingual behavior where applicable;
- navigation and link integrity;
- professional-directory integrity where present;
- privacy, terms, accessibility, and security pages;
- API error behavior;
- branded 404 behavior;
- release and deployment records.

D. EXACT ARTIFACT

- export the same exact candidate SHA;
- verify inventory;
- build one deterministic authoritative ZIP;
- perform ZIP safety checks;
- extract it twice independently;
- run the required suite in both extractions;
- verify all packaged bytes;
- rebuild from a verified extraction and require byte-for-byte identity;
- create a SHA-256 file and concise verification JSON;
- upload evidence with short retention.

E. RELEASE GATE

The job name must be stable and exactly usable as a required check, preferably:

`release-gate`

It must fail unless every required job succeeded.

Do not weaken tests to make the gate pass.

9A. BUILD-ONCE RELEASE MANIFEST AND TREE-EQUIVALENT PROMOTION
===============================================================================

The expensive release gate should produce one authoritative machine-readable manifest, for example:

`deployment/release-manifest.json`

Recommended final shape:

{
  "schemaVersion": 1,
  "portalId": "PORTAL_ID",
  "version": "VERSION",
  "qualifiedCandidateSha": "FULL_SHA",
  "qualifiedTreeId": "FULL_GIT_TREE_OBJECT_ID",
  "qualifiedRunId": 0,
  "releaseGateConclusion": "success",
  "artifactFilename": "EXACT_RELEASE.zip",
  "artifactSha256": "SHA256",
  "artifactSizeBytes": 0,
  "githubArtifactId": 0,
  "githubArtifactDigest": "SHA256_OR_EMPTY",
  "createdAt": "ISO_8601"
}

Rules:

1. Build the release ZIP exactly once from the qualified candidate source tree.
2. Complete the required exact-artifact tests before upload.
3. Upload the ZIP as one immutable workflow artifact, preferably without wrapping the already-zipped file in another archive when the current official action supports single-file non-archived upload.
4. Record the artifact action’s ID, URL, and digest as supplemental evidence; the ZIP’s independently calculated SHA-256 remains authoritative.
5. Never overwrite the qualified artifact name within the same release run.
6. After promotion, calculate `git rev-parse CANDIDATE^{tree}` and `git rev-parse PRODUCTION_BRANCH^{tree}`.
7. If the tree IDs match, create a promotion-proof receipt binding the new production-branch commit to the already-qualified source tree, artifact, and release-gate run. Run only the necessary version, commit, workflow, health-contract, and deployment-source checks on the production branch.
8. If the tree IDs do not match, run the complete release gate against the exact production-branch commit and build a new authoritative artifact for that changed tree.
9. Deploy only the exact current Render-linked production-branch commit unless an explicitly approved rollback target is being deployed.
10. After production smoke succeeds, publish the exact previously qualified workflow artifact to the GitHub Release. Do not rebuild, recompress, rename internally, or substitute a locally regenerated ZIP.
11. Verify the GitHub Release asset SHA-256 after upload and record the release asset ID and URL in production evidence.

This optimization reduces duplicate qualification time without weakening source-byte truth.

10. RENDER CONFIGURATION STANDARD
===============================================================================

Create or update `render.yaml` when it provides a material reproducibility benefit. For an existing Render service, first compare the Blueprint with the observed live service configuration. Validate the file with the official pinned Render CLI. Do not automatically sync or apply a Blueprint to an existing service until service ownership, protected-environment effects, domains, databases, plans, environment groups, preview behavior, and configuration drift are understood.

Use current Blueprint fields, including:

- service name;
- runtime;
- repository and branch where needed;
- root directory where needed;
- build command;
- start command;
- `preDeployCommand` only for safe migrations or required pre-deploy work;
- `healthCheckPath`;
- `autoDeployTrigger`;
- custom domains where appropriate;
- environment-variable names without secret values;
- graceful shutdown setting where useful.

Set `autoDeployTrigger` according to the selected mode:

MODE N — NATIVE ZERO-SECRET

`autoDeployTrigger: checksPass`

Use only when Roger’s authorization is enforced by withholding promotion to the Render-linked production branch and the portal has one stable non-skippable production gate.

MODE H — SERVICE-SPECIFIC EXACT-COMMIT HOOK

`autoDeployTrigger: off`

A hook deployment of a specific `ref` disables auto-deploys. Keep the service off unless the portal is deliberately migrated back to Mode N.

MODE M, C, OR P — DIRECT CONTROL PLANE

Use `off` for exact selected-commit deployment unless the approved control plane deliberately uses `checksPass` and verifies the linked branch.

Do not use `autoDeployTrigger: commit` for a regulated legal portal unless Roger explicitly accepts immediate deployment on every linked-branch change.

Use a Render HTTP health check. The endpoint should perform a minimal operation-critical readiness check, including a simple database query when the database is required.

Do not run destructive database migrations in an ordinary build command.

Set the Render workspace’s overlapping deploy policy deliberately. Prefer `Wait` for these legal portals so an in-progress deploy is not abruptly canceled by another request. GitHub production concurrency should normally prevent overlap before Render sees it, but the Render policy is a second safeguard. Record the observed setting because Render defaults can differ by workspace creation date.

Do not rely on Blueprint defaults. Explicitly set `autoDeployTrigger` for new services. Do not add the deprecated `autoDeploy` field to a new standard. For existing services, confirm the current value after any specific-commit deployment because deploy hooks disable auto-deploys automatically, while Render API and CLI specific-commit deployments do not.

Before syncing a Blueprint to an existing service, export or record every currently managed field. Treat omitted fields as potentially destructive configuration changes. In particular, preserve the existing `buildFilter` intentionally because a Blueprint sync can replace existing filter lists. Verify root-directory-relative commands, domains, environment groups, plans, preview settings, health path, and pre-deploy command after the sync.

11. HEALTH, VERSION, AND ERROR CONTRACTS
===============================================================================

The portal must expose a nonconfidential health endpoint, normally `/health`, returning JSON that allows exact verification.

Recommended fields:

{
  "status": "ok",
  "portalId": "PORTAL_ID",
  "version": "CURRENT_VERSION",
  "commit": "FULL_GIT_SHA_OR_EMPTY_IF_UNAVAILABLE",
  "storage": "postgresql",
  "database": "ready",
  "timestamp": "ISO_8601"
}

Rules:

- return a 2xx status only when the instance is ready for traffic;
- return 503 when an operation-critical dependency is unavailable;
- never expose secrets, credentials, stack traces, private paths, or user data;
- use Render’s documented `RENDER_GIT_COMMIT` runtime value as the primary deployed-commit identity when available; use an explicitly injected identity only for a platform or service type that does not expose it reliably;
- test the endpoint in CI and production.

Keep the Render health path lightweight, deterministic, and free of external services that are not operation-critical. It should normally return exactly `200` when ready and `503` when not ready, even though Render accepts other 2xx and 3xx statuses. Avoid redirects on the health path. Render's platform check requires a response within five seconds and can allow up to fifteen minutes for all new instances to pass before canceling the candidate and leaving prior instances in service. Therefore the deployment controller must allow the platform window, while each individual health request remains fast. Where deeper monitoring is useful, expose a separate nonpublic or access-controlled diagnostic path rather than overloading the deployment health check.

Do not let a `3xx` response that Render technically accepts substitute for application truth. Production smoke must require the portal's intended canonical behavior, exact `200` health response, exact version and commit, and datastore readiness. Use the custom domain as the user-facing acceptance path; use an enabled `onrender.com` service URL only as a diagnostic path to separate application failure from DNS, TLS, or custom-domain routing failure.

The portal must also have a genuine branded 404 contract:

- unknown public routes return HTTP 404;
- the response is useful, branded, accessible, and no-index;
- supported languages remain coherent;
- unknown API routes return a structured API 404, not the public homepage;
- the homepage must never masquerade as a successful missing route.

12. PRODUCTION DEPLOYMENT TRIGGER — FASTEST COMPATIBLE METHOD
===============================================================================

Use this trigger order:

1. For Mode N, promote the exact authorized qualified commit to the Render-linked production branch. The branch update is the deployment trigger; no production workflow dispatch or Render secret is required.
2. For Mode H, C, or P, use direct `workflow_dispatch` through the GitHub REST API when the connected tool can invoke it. Capture the returned workflow run ID and run URLs immediately and monitor that exact run.
3. Use the official Render MCP or connector directly when Mode M is available and the operation is bound to the exact authorized portal and SHA.
4. Use direct `repository_dispatch` only when it is already authenticated, exact-tested, and provides a reliable run-correlation receipt.
5. Use a persistent protected `deployment-control` branch containing one small request file when direct dispatch is unavailable.
6. Use a central-deployer dispatch when the portfolio fast lane is already approved and exact-tested.
7. Use a short-lived `deploy/<version>` branch only when none of the prior methods is available.

The stable `workflow_dispatch` workflow must exist on the default branch. Dispatch the workflow definition from `main`, not from the untrusted release branch. Pass a full target SHA and expected version as typed inputs. The workflow must independently verify the target before checkout and before deployment.

Mode N does not need a secret-bearing dispatch workflow. Its stable production gate must still live on the linked production branch and must independently bind the branch commit to successful qualification evidence.

Do not create a new operations pull request for every deployment unless required by repository policy. Do not create a new version-numbered workflow for each deployment.

The trigger mechanism must be installed once and remain stable across ordinary versions.

For the deployment-control method, maintain one file such as:

`deployment/production-request.json`

Recommended shape:

{
  "schemaVersion": 1,
  "requestId": "UNIQUE_ID",
  "portalId": "PORTAL_ID",
  "targetSha": "FULL_40_CHARACTER_SHA",
  "expectedVersion": "VERSION",
  "requestedAt": "ISO_8601",
  "authorization": "Roger explicitly authorized this release in the current chat"
}

The deployment workflow must not blindly trust the request. It must independently verify:

- the target commit exists;
- the target is the exact current `main` commit or an explicitly approved production tag;
- the version read from the target commit matches the request;
- the exact target commit has a successful `release-gate` or a valid tree-equivalent promotion-proof receipt bound to a successful qualified candidate;
- the production environment is used;
- only one production deployment runs at a time.

The request file contains no secret.

12A. FIRST-DEPLOY DRY RUN AND PREDEPLOY PREFLIGHT
===============================================================================

Before the first production deployment for a portal, and after a material deployment-system change, run a no-write dry run.

The dry run must verify:

- exact target SHA and version resolution;
- target commit exists in the repository;
- target is qualified by the stable `release-gate` or a valid tree-equivalent promotion proof;
- production environment can be referenced;
- the required secret name is present without printing or testing its value against an unrelated endpoint when the selected mode requires a secret; Mode N must explicitly prove that no deployment secret is required;
- portal configuration parses and matches the repository;
- custom domain and TLS respond;
- current `/health` behavior is readable;
- current live version and commit can be classified;
- smoke-route manifest is valid;
- not-found probes are unique and harmless;
- migration classification exists;
- rollback identity is known or explicitly unknown;
- Render service, workspace, linked branch, auto-deploy trigger, and selected mode are coherent;
- no deployment request will be sent.

Record a concise dry-run receipt. A dry run is not production verification and must never be described as a deployment.

12B. DIRECT-DISPATCH INPUTS, RUN CORRELATION, AND NO-BRANCH DEFAULT
===============================================================================

The ordinary production workflow should support stable inputs equivalent to:

- `target_sha`: required full 40-character commit SHA;
- `expected_version`: required release version;
- `mode`: choice of `deploy` or `smoke_only`; keep rollback separate unless a stronger exact-tested design exists;
- `authorization_receipt`: short nonsecret identifier recording that Roger authorized this exact release in the current chat;
- `clear_cache`: boolean default `false`, permitted only for a diagnosed build-cache problem.

The builder should dispatch with the workflow file on `main` and capture:

- workflow run ID;
- API run URL;
- GitHub HTML run URL;
- dispatch timestamp;
- target SHA and expected version;
- authorization receipt.

Record these in deployment evidence without copying confidential chat contents.

Before any Render call, the workflow must verify:

1. input SHA syntax;
2. commit existence;
3. current default-branch relationship;
4. exact version from the target source;
5. successful release gate or valid tree-equivalent promotion proof;
6. matching immutable release manifest;
7. unsuperseded authorization;
8. migration classification;
9. production concurrency ownership;
10. selected deployment mode and required secret presence.

Do not create a deployment branch when direct dispatch works. The branch fallback is for tool limitations, not the default design.

===============================================================================
12C. NATIVE ZERO-SECRET PRODUCTION PROMOTION
===============================================================================

For Mode N, use this exact recurring sequence:

1. Verify Roger authorized the exact portal, version, artifact SHA-256, candidate SHA, and production domain in the current chat.
2. Reconfirm the candidate release gate and immutable release manifest.
3. Reconfirm the candidate descends from the current production source or has an approved migration and promotion plan.
4. Capture the current production branch SHA and current live Render commit as rollback truth.
5. Revalidate that Render is linked to the intended branch and set to `After CI Checks Pass`.
6. Revalidate the stable production gate file exists in the candidate tree.
7. Promote the exact candidate by non-forced fast-forward.
8. If fast-forward is impossible, stop and classify the conflict; do not force-push production.
9. Capture the production-branch update receipt.
10. Monitor the production gate. It must be present and must succeed; zero detected checks is a deployment blocker.
11. Confirm Render starts the deploy only after the gate passes.
12. Monitor the exact deploy directly when available, otherwise poll `/health` for the exact version and `RENDER_GIT_COMMIT` with bounded backoff.
13. Run the full production smoke suite.
14. On success, record the deploy ID or exact live evidence and finalize the existing qualified ZIP, tag, Release, and production handoff.
15. On failure before traffic cutover, leave the prior live instance serving and record the candidate failure.
16. On failure after traffic cutover, apply migration-aware rollback to the distinct previous successful deploy or known-good branch state.
17. Do not perform a second manual exact-commit deploy merely because the native deployment is slower than expected within the documented readiness window.

Do not attach post-deploy polling to the same set of GitHub checks Render must see as complete before it starts the deployment.

===============================================================================
13. RENDER API OR CLI MODE
===============================================================================


When the official Render MCP or connector is available, first use it to retrieve and bind the exact workspace, service, branch, current deploy, and live commit. Otherwise, when the protected environment already contains an approved `RENDER_API_KEY` and `RENDER_SERVICE_ID`, use the official Render CLI pinned to a reviewed version or use the Render API directly. Prefer the pinned CLI for ordinary deployment creation when `render deploys create SERVICE_ID --commit SHA --wait --confirm -o json` provides the required status and logs with less custom code. Capture the machine-readable deploy object and nonzero failure exit directly. Use the API where precise list, retrieve, cancel, or rollback behavior is needed.

The deployment job should:

1. Retrieve the current service and recent deploys.
2. Record the currently live successful deploy ID, commit, and version where available.
3. Compare the live `/health` version and commit with the target.
4. If the exact target is already live, skip the deployment and run smoke verification only.
5. Trigger a deploy with the exact `commitId`.
6. Capture the returned deploy ID.
7. In CLI mode, use `--wait` and machine-readable output; in API mode, poll the Retrieve Deploy endpoint with bounded exponential backoff and rate-limit handling.
8. Stop quickly on a definitive build, startup, cancellation, or update failure.
9. Continue only after Render reports the deploy live or successful. Do not rely only on the public health endpoint when direct status is available.
10. Run the full production smoke suite.
11. If the new deploy became live and smoke fails, roll back to the distinct previous successful deploy ID when rollback is safe.
12. Poll and verify the rollback.

Do not use the API key outside the production job. Do not assume MCP access is narrow: current Render OAuth and API-key access can span all workspaces and services available to the account, so every operation must be allow-listed and product-scoped. Pin the Render CLI version and verify the downloaded binary or installation source. Do not install an unpinned latest CLI during every production run.

Because API and CLI specific-commit deployments do not automatically disable Render auto-deploys, verify `auto-deploy` is off during one-time setup and after any configuration change. Do not toggle unrelated Render service settings during an ordinary deployment.

Do not automatically change Render environment variables, billing, instance types, databases, custom domains, or other service configuration during an ordinary release.

===============================================================================
14. CONTROLLED LOW-FRICTION DEPLOY-HOOK FALLBACK
===============================================================================

Use a protected `RENDER_DEPLOY_HOOK_URL` when it is already configured, when a self-contained manual-deploy workflow is materially safer, or when native CI-gated auto-deploy is unavailable. Mode N is the preferred new zero-secret path; this hook mode is the controlled low-friction fallback and should not be removed merely for uniformity.

Append the exact commit through Render’s supported `ref` parameter.

A specific-commit deploy hook disables Render auto-deploys for the service. Record that change in the onboarding and deployment evidence. Do not later expect `After CI Checks Pass` to resume until the service is deliberately reconfigured.

The script must:

- preserve existing query parameters;
- URL-encode the commit value;
- accept only a full or validated Git SHA;
- use GET or POST as supported;
- treat 200 as started and capture the deploy ID when returned;
- treat 202 as queued, not failed;
- fail on 400, 401, 404, 409, or another definitive rejection;
- never print the hook URL;
- never write it to evidence.

Capture the deploy ID returned by Render on HTTP 200. On HTTP 202, record that the request was queued and that no deploy ID was returned. Hook mode does not itself grant access to retrieve detailed deploy status, so poll the live health endpoint with a bounded timeout and accurate logging unless a separately approved API credential is available for read status. Set the initial bound from the portal’s observed build duration plus Render’s documented new-instance health window and a margin; collect p50 and p95 deployment duration so later runs can use a tighter evidence-based bound. Do not fail a normal deployment prematurely, and do not poll without a hard deadline.

If the target does not become live, report the deployment as unverified. Do not claim success.

Rollback in hook mode may redeploy a distinct verified prior commit only when:

- the new version actually became live;
- the prior commit is known;
- the prior commit differs from the target;
- code rollback is classified safe;
- no irreversible migration blocks rollback.

Never “rollback” to the same commit.

Remember that Render rollback behavior does not necessarily restore current service configuration, custom domains, disks, or all environment-group values. Code rollback must therefore be paired with migration and current-configuration compatibility checks.

A specific-commit deploy-hook request disables Render auto-deploys for the service. Verify and record that resulting state rather than assuming the old setting remained unchanged.

15. IDEMPOTENT DEPLOYMENT CLASSIFICATION
===============================================================================

Immediately before triggering Render, re-resolve and revalidate the request. Confirm the qualified target SHA still matches the authorized main or approved target, the version still matches, the migration classification has not changed, and the request has not been superseded. Use `portalId + targetSha` as the deployment idempotency key. Search current live identity, active and queued GitHub runs, GitHub deployment records, and Render deploy history when directly available. Never create a duplicate request for an identical target that is already live, running, or queued; monitor the existing operation instead. Then classify the action:

A. ALREADY_LIVE

The live health endpoint reports the exact target version and commit.

Action:

- do not trigger Render;
- run production smoke;
- record a successful no-op deployment decision if smoke passes.

B. DEPLOY_REQUIRED_WITH_KNOWN_PRIOR

The live version or commit differs, and a distinct prior successful deploy is known.

Action:

- deploy exact target;
- retain prior deploy ID or commit for rollback;
- smoke test;
- roll back only if the target became live and post-live smoke failed.

C. DEPLOY_REQUIRED_PRIOR_UNKNOWN

The target is not live, but the prior identity cannot be established.

Action:

- deploy only when the portal’s risk classification permits it;
- do not promise automatic rollback;
- preserve Render’s existing zero-downtime behavior;
- report the rollback limitation.

D. BLOCKED

Examples:

- release gate absent or failed;
- target is not approved main/tag;
- migration is destructive or unclassified;
- required secret is missing;
- domain or health endpoint is unavailable in a way that prevents safe verification.

Action:

- do not trigger production;
- report the precise blocker;
- ask Roger only for the minimum necessary owner action.

===============================================================================
16. DATABASE MIGRATION SAFETY
===============================================================================

Classify every production release:

- NO_MIGRATION;
- BACKWARD_COMPATIBLE_EXPAND;
- BACKWARD_COMPATIBLE_DATA_CHANGE;
- CONTRACT_AFTER_COMPATIBILITY_WINDOW;
- DESTRUCTIVE_OR_IRREVERSIBLE;
- UNKNOWN.

Automatic deployment and rollback are allowed only when the classification supports them.

Preferred migration method:

- expand first;
- deploy code compatible with old and new schema;
- verify;
- contract only in a later release after a compatibility window.

Use Render `preDeployCommand` only for migrations that are safe to run once per deployment and are tested for retry behavior. Prefer idempotent migration units, a durable migration ledger, database transactions where the engine and operation support them, bounded locks, and an expand-and-contract sequence. A failed pre-deploy command can leave the old application live while still leaving partial database side effects; inspect migration state before retrying or rolling back.

Code rollback does not roll back the database, persistent disks, or externally changed state. Never automatically roll back code across a destructive or incompatible migration.

Stop for Roger’s explicit decision before an irreversible production migration.

17. PRODUCTION SMOKE SUITE
===============================================================================

Create a stable, version-agnostic smoke script driven by configuration. Use bounded retries only for startup propagation and transient network responses. Once the health endpoint reports the exact new commit, treat subsequent material smoke failures as post-live failures. Do not hide a persistent defect with unlimited retries.

At minimum verify:

1. HTTPS and canonical-domain behavior.
2. `/health` returns 2xx, expected portal ID, exact version, exact commit, and required database readiness.
3. Homepage returns 200 and expected portal markers.
4. Primary public starting route returns 200.
5. Privacy, terms, accessibility, and security routes return expected statuses and markers where present.
6. Professional directory returns 200 when the portal has one.
7. At least one representative professional profile or directory result works when applicable.
8. The branded missing-route probe returns 404, contains expected portal/language markers, and does not contain the homepage hero.
9. Unknown API route returns the correct API 404.
10. Critical static assets, favicon, sitemap, and robots behavior are valid where applicable.
11. No response exposes a stack trace, secret, private path, or internal development wording.
12. Redirects do not loop.
13. Content-language behavior is coherent for the portal’s approved languages.

Use a JSON route manifest rather than hardcoding every portal route in the workflow.

Do not fail a deployment for a nonmaterial wording change unless the wording is part of a safety or identity contract.

Do fail for wrong version, wrong commit, 5xx, broken health, missing primary route, soft 404, inaccessible critical navigation, or another material release claim.

===============================================================================
18. RENDER FAILURE AND ROLLBACK LOGIC
===============================================================================

Use Render’s immutable, zero-downtime deployment behavior correctly.

If the new build or new instance fails before Render routes traffic to it, including a new instance that never passes Render’s health gate within the platform timeout:

- the old service normally remains live;
- do not trigger an unnecessary rollback;
- report the failed candidate and preserve the existing production service.

If Render reports the new deploy live and the independent production smoke then finds a material defect:

- roll back to the distinct previous successful deploy when safe;
- prefer Render’s rollback endpoint and previous deploy ID because it can reuse build artifacts and is faster than rebuilding an old commit;
- verify the rollback health, version, and commit;
- disable or prevent conflicting auto-deploy behavior where necessary.

Do not roll back for a harmless monitoring assertion that does not reflect a real platform defect. Repair the smoke contract instead.

Do not call a same-commit redeploy a rollback.

Use these required failure classifications:

- `REQUEST_REJECTED`: Render did not accept the request; production is unchanged.
- `QUEUED`: Render accepted a waiting request; success is still unknown.
- `BUILD_FAILED`: candidate build failed before cutover; prior production remains live.
- `PREDEPLOY_FAILED`: migration or pre-deploy command failed before cutover; prior production normally remains live, but database side effects must be reviewed.
- `START_FAILED`: candidate did not start; prior production remains live.
- `HEALTH_GATE_FAILED`: candidate never became healthy; prior production remains live.
- `LIVE_SMOKE_FAILED`: candidate became live but independent smoke found a material defect; rollback may be required.
- `ROLLBACK_LIVE`: distinct known-good prior deploy is live and verified.
- `ALREADY_LIVE`: exact target was already production verified; no deploy occurred.

For all pre-cutover failures, verify the old live version rather than issuing a reflexive rollback. For `LIVE_SMOKE_FAILED`, prefer Render’s retained-build rollback when available and migration-safe. Treat that operation as an application-build rollback, not a universal infrastructure or data restore. After rollback, re-verify current custom domains, instance type, persistent disks, environment groups, runtime platform, health path, exact commit, version, and datastore compatibility. After any rollback, apply the quarantine rule before re-enabling ordinary auto-deploy.
